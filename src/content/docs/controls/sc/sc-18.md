## Control statement

- **a.** Define acceptable and unacceptable mobile code and mobile code technologies; and
- **b.** Authorize, monitor, and control the use of mobile code within the system.

<details>
<summary>NIST discussion</summary>

Mobile code includes any program, application, or content that can be transmitted across a network (e.g., embedded in an email, document, or website) and executed on a remote system. Decisions regarding the use of mobile code within organizational systems are based on the potential for the code to cause damage to the systems if used maliciously. Mobile code technologies include Java applets, JavaScript, HTML5, WebGL, and VBScript. Usage restrictions and implementation guidelines apply to both the selection and use of mobile code installed on servers and mobile code downloaded and executed on individual workstations and devices, including notebook computers and smart phones. Mobile code policy and procedures address specific actions taken to prevent the development, acquisition, and introduction of unacceptable mobile code within organizational systems, including requiring mobile code to be digitally signed by a trusted source.

</details>

## How to apply it

SC-18 asks you to decide which mobile code is acceptable and which is not, then authorize, monitor and control its use in the system. NIST's discussion defines mobile code as any program, application or content sent across a network, for example embedded in an email, document or website, and run on another system; it names JavaScript, HTML5, WebGL, VBScript and Java applets. Base the decision on the damage the code could do if used maliciously, and apply it both to code installed on servers and to code downloaded and run on workstations, laptops and phones. SC-18 is in the Moderate and High baselines, not Low.

**Common implementations.** Few organizations can block JavaScript, so the definition is usually by technology and source rather than a blanket ban:

- Office macros: blocked in files from the internet, and allowed only when signed by a publisher the organization trusts. NIST's discussion names requiring mobile code to be digitally signed by a trusted source as one of the policy's measures.
- Browsers: managed through central policy, with extensions limited to an approved list, legacy plug-ins and Java applets not allowed, and downloads screened by the web gateway.
- Scripts that run on endpoints, such as PowerShell or other scripting languages: restricted to signed scripts or to administrators, and logged.
- Email attachments with scripts, executables or macro-enabled documents blocked or quarantined at the email gateway.
- On servers and in web applications, a content security policy that limits which script sources a page will run, and third-party scripts loaded only from approved sources with integrity checks.

Enforce these through configuration settings, so they appear in the baseline configuration ([CM-6](/controls/cm/cm-6/)) rather than in user training alone. [NIST SP 800-28 Version 2](https://csrc.nist.gov/pubs/sp/800/28/ver2/final), Guidelines on Active Content and Mobile Code (March 2008), covers the threats and safeguards for end user systems; it predates current browsers, so use it for the concepts and the vendor's current settings for the details.

**Organization-defined parameters.** SC-18 has no parameters. In the [System and Communications Protection policy](/templates/policies/sc/), the Chief Information Security Officer defines acceptable and unacceptable mobile code and mobile code technologies, and the system owner authorizes, monitors and controls its use within the system. Put the definition where people will find it, for example as a short list in the procedures that support the policy or in the baseline configuration, by technology: allowed, allowed with conditions (signed, from approved sources, administrators only) and not allowed.

**Evidence assessors ask for.**

- The written definition of acceptable and unacceptable mobile code
- Office application policy settings for macros, browser policy settings for extensions and plug-ins, and script execution policy, exported from the management tool
- Email and web gateway rules that block or quarantine unacceptable attachments and downloads
- For web applications the system serves, its content security policy and how third-party scripts are approved
- Logs or alerts that show blocked mobile code, which is how the monitoring in SC-18b is shown ([AU-2](/controls/au/au-2/), [SI-3](/controls/si/si-3/))

**Inheritance.** Endpoint, browser, office and email gateway settings are usually common controls, set once by the endpoint and messaging teams. The system owns the mobile code its own application serves or runs, such as scripts, plug-ins and third-party components in its web pages, so SC-18 is often a hybrid control. Record the split in the [system security plan](/templates/plans/system-security-plan/).

**Common findings.**

- No written definition, only a statement that "mobile code is controlled".
- Macros allowed from any source, or the "block macros from the internet" setting not applied to all devices.
- Browser extensions unmanaged, so users can install any extension, including ones that read every page.
- A public web application loading scripts from many third-party sources with no content security policy.

**Enhancements in the Moderate baseline.** SC-18 has no enhancements in any baseline. [SC-18(1)](#sc-18.1) identifying unacceptable code and taking corrective actions, [SC-18(2)](#sc-18.2) acquisition, development and use, [SC-18(3)](#sc-18.3) preventing download and execution, [SC-18(4)](#sc-18.4) preventing automatic execution and [SC-18(5)](#sc-18.5) execution only in confined environments are in no baseline. The common implementations above already meet much of SC-18(1), (3) and (4): NIST's discussion of SC-18(1) gives blocking word processing files with unacceptable macros as an example, and of SC-18(4), disabling auto-run for portable storage devices.
