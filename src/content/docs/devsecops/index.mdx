This section is for teams that build and run a system through a CI/CD pipeline and need it authorized under the RMF. It shows, one topic at a time, how the pipeline meets the controls and which of its outputs an assessor will accept. It covers vendor-neutral process and evidence, with the status of each source as of October 2026.

DevSecOps covers the systems a team builds and runs, and the controls that the pipeline and infrastructure as code deliver. It does not cover how people, physical or governance controls are met, or purchased software the team neither builds nor runs. Platform settings, such as how to configure a particular cloud or Kubernetes service, belong in the [technology playbooks](/technology/).

## How each page is built

Every topic page follows the same chain, from the requirement down to the evidence:

| Part | What the page uses |
| --- | --- |
| Requirement | The RMF and SP 800-53: the guide's [control pages](/controls/), with the SP 800-53A objectives that matter |
| Structure | The NIST publication for the topic: SP 800-128 for change and configuration, SP 800-40 for findings and remediation, SP 800-204D for the pipeline, SP 800-137 for continuous monitoring, and for building software the SSDF, with the NCCoE's draft DevSecOps practice guide (SP 1800-44) |
| Team practice | OWASP DevSecOps Guideline sections, DSOMM activities and the OWASP Top 10 CI/CD Security Risks, cited by name and ID; the DoD DevSecOps Activities & Tools Guidebook as the government cross-check |
| Evidence | The SP 800-53A assessment objectives and methods (examine, interview, test), and the pipeline output that meets each; FedRAMP 20x Key Security Indicators as a labelled model |

Where NIST settles a question, the page follows NIST. Where it does not, the page gives practice that should pass an assessment, and says so.

## How it relates to the rest of the guide

- **Control pages** say what each control requires. Each topic page names its controls in front matter, so it appears under "Referenced by" on those control pages.
- **[Templates](/templates/)** are the program documents. A topic page says which templates to use, and changes a template where a pipeline changes what the template should say.
- **Methods** are NIST's published ways of meeting controls, starting with the SSDF; they are being added in Phase 4 of the [roadmap](/reference/roadmap/). A topic page cites the method that structures it.
- **[Technology playbooks](/technology/)** hold the platform settings. A topic page stops at the vendor-neutral process.

## The seven steps for a system that ships through a pipeline

[SP 800-37 Rev. 2](https://csrc.nist.gov/pubs/sp/800/37/r2/final) applies the RMF to any type of development approach, "including Agile and DevOps approaches". The steps and tasks do not change; what changes is where their outputs come from.

| Step | What changes for a pipeline team |
| --- | --- |
| [Prepare](/rmf/steps/prepare/) | Decide whether the pipeline (source repository, build runners, artifact registry, deployment identity) sits inside the authorization boundary (task P-11) and list its components as assets (P-10). Identify what a platform provides as common controls (P-5). |
| [Categorize](/rmf/steps/categorize/) | Describe how the system is built and deployed in the system description (C-1). Deployments rarely change the categorization, but a new information type does, and is a significant change. |
| [Select](/rmf/steps/select/) | Set parameters to fit the pipeline, such as the change control body that oversees a preapproved pipeline class (S-2). Write in the system security plan which controls the pipeline implements (S-4), and which pipeline outputs feed monitoring (S-5). |
| [Implement](/rmf/steps/implement/) | Many technical controls are implemented as code: infrastructure, configuration and gates (I-1). The as-implemented state is read from version control and recorded (I-2). |
| [Assess](/rmf/steps/assess/) | Plan to use pipeline outputs as evidence, and to sample from deployment history (A-2). The assessor still examines, interviews and tests (A-3). |
| [Authorize](/rmf/steps/authorize/) | The authorizing official's terms and conditions can define significant change for the system and accept a preapproved pipeline class (R-4). |
| [Monitor](/rmf/steps/monitor/) | The pipeline is where most change happens, so it is where change is monitored (M-1). Its outputs feed ongoing assessments (M-2) and ongoing authorization (M-6). |
